# V4 故事里程碑：3/16 → 3/22 七日弧

设计目标：把"种子 → 3/22 中庭 3·16 台风纪念活动"的目标结局拆成**可量化、
逐日可检查**的里程碑。每天跑完后用 `scripts/check_milestones.py
runs/<artifact>.json --day N` 验证；未通过时按 §3 的归因流程定位。

里程碑是**下限不是剧本**：检查的是"这一天世界上是否发生了至少这些事"，
不规定角色怎么做。检查器是纯函数（事件/发言的模式匹配），不含 LLM 调用。

## 1. 总弧线（为什么是七天）

3/16（周一）是第一天；种子排程的"3·16 台风纪念活动"落在**下周日 3/22**
（中庭，招募志愿者整理老照片和旧记录）——它是 2013 年台风真相自然公开的
唯一舞台，因此是七日弧的终点。三条主线在七天内收束：

| 线 | 3/16 状态 | 终局（3/22） |
| --- | --- | --- |
| 2013 台风真相 | 台账 22:05 vs 导出件 23:30 差异被两位主角记录；老周托话未达实质 | 签名人（老街坊代表）与目击缺失当众对质；老赵头被点名 |
| 陈默 × 林瑶 | "我来处理"式帮忙与程序性共处；九岁承诺未提 | 那句完整的话（为什么走+对不起）当面试验 |
| 学生会审计 / 唐小岚 | 催办单转达；小岚记着"待核实"的草稿 | 审计了结；草稿归属与"故事能杀人"的抉择落定 |

## 2. 逐日里程碑

每天的检查项是 `scripts/check_milestones.py` 中 `MILESTONES[N]` 的数据
（与本表一一对应）。密度大的日子拆上下半（半天 = 一个检查组）。

## 3. 未达标归因流程

某项 FAIL 时按顺序归因，结论记入当天的工单：
1. **事件被触发但角色没接** → 提示词/人设太保守（NPC 分寸线、MC 目标
   强度），改种子措辞或 director 简报；
2. **事件根本没被触发** → 排程/唤醒缺失（引擎层，如 ticket-24 的
   same-batch 生成 bug），修引擎；
3. **里程碑要求超出当日世界可达状态** → 里程碑太激进，后移一日并在本文
   记录变更原因；
4. **角色行为合理但检查器模式没匹配上** → 改检查器模式（记录变更）。

判据示例：d4-老赵头 FAIL 且日志里大爷从未被点名唤醒 → 情形 2；大爷被
唤醒且人设分寸线明确说"今天不说" → 情形 1 或 3。

## 4. 校准说明（诚实记录）

- 第 1 天的检查项是在 **3/16 实际运行完成后**校准的——它们描述"这一天
  至少发生了什么"，天然向后一致（10/10 PASS）。这是校准基线，不是预言。
- 第 2–7 天的检查项是**前瞻设计**：当前种子只排程了第 1 天，第 2 天起
  需要逐日补充排程与种子。检查模式（哪些词算"真相点名"）应随种子细化
  同步修订，修订记录在本文 git 历史里。
- 检查器证据行是首条命中，不代表全部；细节以轨迹 JSON 为准。
