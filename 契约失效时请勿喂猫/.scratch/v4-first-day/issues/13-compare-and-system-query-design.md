# 13: compare 的存在意义 + system_query 的语言与选项呈现

## 问题一：compare 为什么存在？还有必要吗？

**原始设计动机**（V4-DESIGN 台账轴心）：
1. 台账 vs 导出原件的时间戳差异是 2013 线的核心证据——"借出记录被改"这个事实需要一条**客观发现通道**，不能靠作者旁白塞给角色。
2. 判定权威性：由世界（引擎）宣告"不一致"，而不是模型自己读完两份后在上下文里脑补差异——防止幻觉差异污染剧情（模型说"不一致"与世界说"不一致"在编年体里分量不同）。
3. 社会可见性：document_compared 事件对同地者可见——"当众比对"是一个真实的调查动作，别人看得见你在查。

**反方（用户直觉的合理性）**：
- 模型完全可以 read 两份后在 inner 里自己比对——read 结果本来就进了上下文。compare 的增量信息只有"世界盖章"这一点。
- 实测使用率两极：第一天 run 里 26 次 compare（大半是刷），现在一轮 1-2 次。刷的那部分就是零信息废回合。
- 多一个工具 = 多一份 schema/描述/affordance 维护面。

**候选裁决**：
- (a) 保留现状——判定权威性 + 公开动作语义足够独特。
- (b) 删除 compare，靠 read + 模型自行 diff——工具面再减一，但失去世界盖章与公开事件，"发现被改"变成模型私有推断，编年体里不再有"陈默 比对 A 与 B"这一客观动作行。
- (c) 保留但加门槛——compare 只在两份内容确实不同时才消耗 tick？不行，这泄露答案（世界先验地告诉模型该不该比对）。不采纳。
- (d) 保留但结果更丰富——"内容不一致"之外附上首个差异片段的定位提示（如"导出件的时间戳与纸质页对不上"），让发现通道更有戏。

**倾向**：(a) 或 (d)。理由：这条 mechanic 是台账剧情的骨架；删掉后"发现"变成模型脑内行为，编年体失去一个客观调查事件。d 成本低且直接回应用户"not really helpful"的观感。

## 问题二：system_query 的语言与选项

用户两点：
1. **应该中文**——同意，且这不只是语言问题：台账是超自然参与者，query 被拒是它的**世界内行为**（它不想答/答不了），不是引擎协议错误。英语 "question is outside the Ledger's objective fact table" 是协议腔漏进了世界观。docs §0 语言分工说"机制类错误英文"——但这条应该归类为"台账的世界内拒绝"，走中文。
2. **选项有限就该给出**——同意。事实表是种子固定的小集合（manifest `system.facts` 键），逐字匹配 + 隐藏键名 = 抽奖（实测 queries_used 0/1 一次浪费）。台账在叙事里已经"宣读条款"（accept 事件），把**可问的问题清单**作为条款的一部分呈现完全符合世界观：台账说"你可以问我这几件事"——给出键名，不给出答案。候选实现：
   - (i) system_query 的工具描述里写死？不行——事实表是种子数据，工具描述是静态的。
   - (ii) affordance 行枚举：`[system_query] question=2013年台风台账的借出时间`（每键一行或合并）——键名直接可抄，消除猜测。
   - (iii) 台账首次接案叙事里附清单（#events 私有投递行）。
   - (ii)+(iii) 组合最优：affordance 可抄，叙事有来历。
