# 31 — 工具报错的“合法示例”把私密消息改发给错误的人

Status: ready-for-agent
Need-review: yes
Need-test-cases: yes

## 复现与根因
半天工件 `v4/runs/real-20260928T170943+0800-1005580-081751820.json`：08:54 陈默妈试图向李阿姨 `text` 询问 2013 年家属院撤离文书等私事；工具正确拒绝未知联系人，但错误信息随后附 `Valid call: text(target=林瑶, text=原封不动写给李阿姨的全文)`，第二个候选是陈默。若照示例调用即把明确面向李阿姨的私密询问错发给另一人。实际工件没有证据显示她照做，属高风险误导，不宣称已泄漏。

根因：`engine._action_rejection_text` 对 `exc.alternatives` 的 `text <contact>` 不考虑原 target 的语义关联，机械复用原消息正文并生成合法但错误的收件人调用；无候选时也从 `world.affordances` 取首个同类目标。`speak` 等有 target 的工具可能同型。报错中的调用必须不仅语法合法，还要**保留用户意图的收件人**，否则不能被标成“你可能指的是”。

## 验收
未知联系人时列出可用正式联系人、如何建立 `!contact` 行或改成现场交谈/留给后人的字条，但不得以原正文生成发给无关人的调用示例。只有高置信唯一别名/实体同义时才可给保留意图的示例，且注明确认收件人；多义时拒绝并列候选而不填原正文。`speak` 不在场、`give` 目标不可达等同理。回归测试以“李阿姨”失败、林瑶与陈默可联系为例，断言错误**不**包含改发林瑶的原文调用。

- 2026-09-28, pi：这是工具 helpfulness 的安全底线；正确拒绝比错误可执行建议更好。
