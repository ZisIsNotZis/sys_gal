# V5 三层：引擎、库、种子

本文件规定"什么能写在哪"，以及**按需具体化**的执行方式。它约束的是作者与 agent 的手，不是运行时的行为。

## 1. 三层与三个受众

| 层 | 拥有什么 | 谁读它 | 改动成本 |
| --- | --- | --- | --- |
| **引擎** `v5/engine/` | 十条原始项、解析、编排、重放、检查点 | 只有引擎自己 | 最高：要重证历史失败台账 |
| **库** `v5/library/` | 物性、规则、渲染、例外模式：可复用的常识 | 引擎加载它；模型通过它看见动词 | 中：一概念一测试 |
| **种子** `v5/stories/<故事>/` | 实例、地点、卡司、制度、排程、例外、初始状态、验收 | 作者与检查器 | 低：改一支故事不碰引擎 |

三个受众不许混：**引擎内部只有原始项；模型只看见由库生成的日常动词；种子只写这一部作品的具体事实**。引擎里出现故事名词是耦合，提示里出现状态键是泄漏，种子里出现逻辑是失控。

## 2. 按需具体化：粗到细的阶梯

默认停在最粗的那一级，只有当**某个故事的验收在不具体化的前提下无法成立**时才下沉一级。

以"写"为例：

| 级 | 表达 | 何时才允许停在这里 | 下沉触发 |
| --- | --- | --- | --- |
| 1 | 这东西能被写 | 任何故事都能写上去 | 需要区分"能不能擦掉" |
| 2 | 钢笔写的擦不掉，铅笔写的能擦 | 《借条》的验收依赖它 | 需要区分"遇水会化" |
| 3 | 这支笔的墨遇水会化，那支不会 | 某场戏的验收依赖它 | 需要区分"写的时候有人在看" |
| 4 | 在这个位置写会被看见，在那个位置不会 | 需要"当众/私下"的物理差异时 | 不再下沉 |

**下沉的代价是一次四件套**：一个失败的场景（证明不具体化就过不了验收）、一条规则、一个渲染、一个测试。缺任何一件，下沉被拒绝。

## 3. 进库判据

一个概念可以进 `library/`，只有两条路：

1. **至少两支故事用到**（"没有孤儿概念"）；
2. **它一次消掉一整类绕路**（例如"复制"一次消掉"抄件只能由种子写死"）。

不满足的，留在种子层做**局部覆盖**：声明式、lint 可见、带一句"为什么现在不上升"。第二次用到时再上升，不许提前上升。

## 4. 一个库概念由什么组成

概念不是一段代码，是五件东西，少一件不算完成：

| 部件 | 内容 | 例（写） |
| --- | --- | --- |
| **物性** | 它要求对象具备的属性 | 表面接受某类痕迹；工具能留下该类痕迹 |
| **规则** | `when` / `do` / `cost` / `render` / `fail` | 见 `V5-PRIMITIVES.md` §3 P9 |
| **渲染** | 参与者各自看到什么、听到什么 | 作者看到"笔尖在纸上过去"；旁人看到"他在写字"，看不到内容 |
| **失败** | 不成时的回执与可行清单 | "这张纸现在写不上：桌上没有能留下痕迹的东西" |
| **测试** | 至少一条成功、一条失败、一条"别人看不见" | 三条都要 |

另外两个必填字段：`since`（版本）、`used_by`（哪几支故事用到，孤儿检查读它）。

## 5. 种子里能写与不能写

**能写**：实例与地点、卡司与其知识、制度与班次、排程、初始状态、局部覆盖、本故事的验收判据。

**不能写**：

- 逻辑（任何 `if`/循环/计算）——那是规则的事；
- 引擎真相（谁写了什么、谁读过什么）——那是事件的账本，不是世界的事实；
- **对具名角色的祈使句**（"让陈默去交说明"）——见 §7。

判断标准一句话：**种子写"世界是什么样"，不写"接下来发生什么"。**

## 6. 局部覆盖与升级

种子里可以出现"只有这台复印机会卡纸"这种只对一件东西成立的表述。它必须是：

- 显式：`override: {规则名: {条件}}`，不许隐式改变规则；
- 可查：lint 列出全部覆盖及其所在故事；
- 有注记：一句为什么它还没进库。

同一个覆盖出现第二次，就必须上升为库概念（或证明两者其实不同）。

## 7. 反作弊：种子的三条禁令（可机械检查）

1. **没有对具名角色的祈使句**：种子里不出现"让某人去…""某人应当…"。检查：对卡司名做祈使句式扫描 + 人工复核。
2. **没有天意事件**：排程效应必须是物理或制度（有人上班、门几点关、谁值班、哪张纸放在哪），不许是"命运让灯坏了"。检查：每个排程效应都要能指到一个制度或物性。
3. **预期结局不是唯一可达结局**：每条被期待的路，至少要能指出另一条物理可行的路。

## 8. 目录布局

```text
├── library/          # 概念：物性 + 规则 + 渲染 + 失败 + 测试 + used_by
│   ├── concepts/
│   └── CHANGELOG.md
├── stories/
│   ├── s1_last_bus/         # 《末班车》：种子 + 卡司 + 验收 + runs/
│   ├── s2_borrow_note/      # 《借条》
│   ├── s3_night_market/     # 《夜市》
│   ├── s4_night_shift/      # 《夜班》
│   ├── s5_wedding/          # 《婚礼》

```

## 9. lint 的职责（机械可判）

- 所有引用可解析（实体、地点、概念、规则名）。
- 每个状态键都有渲染模板，反之亦然。
- 每条规则引用的属性存在；每个属性至少被一条规则用到。
- 每个库概念的 `used_by` 至少两支故事（孤儿检查）。
- 引擎源码里不出现任何故事名词（种子实体名、地点名、卡司名）。
- 种子无祈使句、无天意事件（§7）。
- 局部覆盖全部被列出并带注记。

## 10. 智能体表面（一眼、最近、知识、检索、回想）

一个角色每回合拿到的东西由引擎生成，不由故事手写：

| 部件 | 内容 | 规则 |
| --- | --- | --- |
| 一眼 | 时间、所在、眼前有什么、手里有什么 | 只见物理：纸上"上面有字"，看不到内容 |
| 最近 | 他实际感知到的最近几条，逐字 | 只来自他自己收到的投递 |
| 知道的事 | 他相信的事（身份、常识、对人的看法） | 可能错、可能旧，世界不替他纠正 |
| 细看 | 把眼前的东西看到细节（怎么写的、有没有折痕） | 仍不给正文 |
| 读 | 取得正文 | 这是唯一得到内容的动作，且只进自己的记忆 |
| 检索、回想 | 在**自己**的记忆里按字面找 | 找不到就是找不到，没有语义猜测 |

两条硬规则：**上下文只含他自己感知过或相信过的东西**；**每回合把这份上下文连同他的动作一起记进轨迹**，否则"他当时知道什么"无法审计。

系统提示（角色的身份与处境）由种子的 `identity` 与库的动词表生成，不许在每支故事里重写一份——否则同一件事就有两个家。

这一层不新增原始项：它只是 P6（感知投递）与 P7（心智）的一个视图。

## 11. 版本与变更

- 概念带 `since`，破坏性变更升主版本并在 `CHANGELOG.md` 写明迁移。
- 一支故事声明它写作时对齐的库版本；库的破坏性变更必须同时给出所有故事的迁移，不许让故事悄悄失配。
- 引擎的破坏性变更必须重跑历史失败台账，与 v4 的做法一致。
