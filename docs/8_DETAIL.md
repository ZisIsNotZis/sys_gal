# DETAIL — 模块内部

只写模块内部怎么成立：原始项逐条、时钟、检查点、期限、盘点、反作弊三检，以及运行暴露过且现在仍然成立的缺陷。层与层的边界在 `docs/6_ARCHITECTURE.md`，文件与参数形状在 `docs/7_INTERFACE.md`。

## EXPLICIT

### 十条原始项：含义与"不含什么"

- **P1 实体**：一个身份号（单调递增、永不复用）+ 一个扁平的类型标签，仅此。其余九条都是"关于某个东西"的，所以身份必须稳定，否则重放与检查点无法对齐。**不含**名字（那是 P10 与语言）、类型继承（分类学属于库）。
- **P2 状态**：`实体 → {键: 值}`。键的语义与值的类型由库声明，引擎只负责存取与事务性；一次意愿内的全部写入必须原子生效或全部不生效。**不含**历史（P5）、解释（"这是一份说明"是知识，不是状态）。
- **P3 包含**：`实体 → 父（地点或容器）`，一棵树，地点也是实体。拿、放、递、翻找、装、搬全部建立在它之上。**不含**距离与路径（路程是库概念在地点图上的时间代价）、"隐藏"（可见性是状态键）。
- **P4 时间**：单调时钟 + 排程表（到点触发）+ 动作可带耗时。带耗时的动作是一段**区间**：落在区间里的到期效果按时间顺序先发生，然后在它们留下的新世界上把规则重新问一次。**不含**日历语义（工作日、节日是库/种子的事实）、随机（随机是 `(种子, 事件号)` 的纯函数）。
- **P5 事件**：`{事件号, 时间, 种类, 主体, 客体, 状态增量, 因果}` 的不可变记录，是世界的账本，不是任何人的知识。**不含**可感知性：事件永不直接进入心智，进心智的只有 P6 投递的渲染结果。
- **P6 感知投递**：一条"某事件经某通道到达某心智"的投递，附渲染文本（该心智实际感知到的内容）与保真度。它是世界真相与角色知识之间唯一的闸门。**不含**内容的解释：渲染里只有物理（字、墨色、声音、动作），不含作者、时间戳、读者、因果。
- **P7 心智**：带记忆与知识的实体。记忆是感知投递的累积；知识是概念、实体、关系、程序；另有当前意愿与在飞动作。**不含**"事实"——记忆可以是错的、缺的、被后来的话污染的，这由库的保真度规则决定，引擎只存与取。
- **P8 意愿**：心智提出的 `(动词, 已解析的客体, 期望)`。引擎按规则判合法，然后要么产生效果与事件，要么产生拒绝回执（为什么不成、眼前可行的有哪些）；它可以被中途打断。**不含**动词表（动词是库概念）。
- **P9 规则**：`when`（对物性、状态、包含、持有、知识的条件）+ `do`（原子效果）+ `cost`（时间）+ `render`（参与者看到的）+ `fail`（失败与可行清单）。**纯函数**：只依赖状态、时间与 `(种子, 事件号)`。原子效果的封闭集（代码名）：`set`、`unset`、`move`、`create`、`destroy`、`remember`、`know`、`clock`、`schedule`、`unschedule`、`flag`。**不含**任意代码、概率分支、把作者意图写进 `when`。
- **P10 命名解析**：把一个心智说出的指称（名字、别名、描述、指代、序数）解析为一个实体，**只允许用该心智此刻能感知与已知的东西**；歧义时按确定性规则挑选并说出来，或者回问；完全无解时返回"这里现在有什么"的可行动清单。**不含**命名策略（别名来源、称呼的礼貌层级都是库/种子）。

四条守则是原始项的可检查面：引擎永不凭空造痕（任何状态只能由声明过的规则写入）；每个状态键成对给出渲染（内容永远只能由有代价的动作取得，不随"看一眼"白给）；事件不可感知（渲染里不许出现作者、时间戳、读者、因果）；规则是纯函数（不读墙钟、不 IO、不外部随机）。

**分辨率常数**：世界的事实分辨率 = 一个用心观察的普通人，不带仪器、一眼或一次细看能注意到的东西。字迹、折痕、撕口、破损、湿痕、气味、谁的衣服湿了、谁手里攥着什么，都在此之内；指纹、笔压、纤维、墨水的化学成分，都在此之外。越过这条线的需求，要么改成"某个表面声明了浮灰/水痕"这种通用状态，要么明确写进非目标。

### 时钟与日期翻日

世界时钟是从开局起算的分钟数。`clock_label(minutes, date)` 是唯一的读法出口：

- 给了日期：按 1440 分钟翻日，`base_date + 天数` 印成 `YYYY-MM-DD HH:MM`。所以 `1920` 是次日的 `08:00`，不是 `32:00`。
- 没给日期：只能印出从开局算起的 `HH:MM`（`1920` → `32:00`）。这条分支不是备用，它是负向对照——同一个数在两种读法下不一样，说明翻日是日期做的，不是格式化的巧合。

日期来自种子的 `date`，进 `World.digest()`；时钟的每一次推进都落成一条 `tick` 事件（`advance_to`），排程被消费时也落 `unschedule` 原子效果——否则重放出来的世界里那条排程还挂着。

### 检查点：格式与续跑为什么因果连续

文件格式 `v5-checkpoint-1`（UTF-8 JSON）：顶层 `format`、`label`（人读的断点名，不参与还原）、`clock`（人读；权威值是 `world.clock`）、`event_count`、`events`（账本前缀）、`digest`（`world.digest()`）、`world`。`world` 的字段与世界对象的可变字段一一对应：`clock`、`date`、`seq`、`entities`、`state`、`parent`、`schedule`、`memory`、`knowledge`、`beliefs`、`hand_readers`、`flags`。

读回时 `validate` 拒绝任何不合：格式不认识、`event_count` 与账本条数不一致、事件 id 不是 `1..N` 连续。`restore` 还原世界后必须与记录的 `digest` 一致，否则拒绝。写入用"临时文件 → `os.link` 到正式名 → 删临时文件"：目标已存在即失败，绝不覆盖；同一 `run_id` 的检查点按两位序号递增成一条序列。`seq` 必须存：它决定同一时刻两条排程的先后，而 `digest` 看不见它。`entities` 必须按插入顺序存：同一场地里"先投递给谁"由实体顺序决定，顺序变了世界仍是同一个 digest，账本却不是同一本字节。

**续跑为什么因果连续**：检查点存的是**状态**，不是剧本位置——世界（实体、状态、包含、时钟、排程、心智、旗标）加事件账本的前缀。续跑 = 从检查点还原二者，再让同一份脚本或演员往下走；新事件接在旧编号之后，前缀逐字节相同。因此"从种子整本重放"与"检查点续跑"必须是同一个世界。引擎没有单独的版本号字段：世界的一致性由逐事件的 `digest_after` 负责，事件的身份由 ordinal（已有条数 + 1）负责，检查点断言用这两样。

### 期限与在飞动作的中途打断

调用方把世界效果表交给 `submit(..., effects=…)` 时，一个带耗时的动作就是一段**区间**：先让已经到期的效果发生；然后在动作完成之前，只要还有到期点落在区间里，就把时钟走到那一点、执行那批效果，再在**新世界**上把规则重新问一次（实体是否还在、`when` 是否仍成立）。前提被抽走，这个动作就做不完。

做不完不是"没成"：

- 效果一个都不留（P2 的原子性），时钟停在截断那一刻（时钟已由 `tick` 事件推到这里）。
- 本人留下的记忆是"你的动作停在半路，没能做完"；在场的人看到"动作停在半路"，没有解释、没有事件层元数据。
- 账本落一条 `kind="interrupted"` 的事件，`note` 带 `reason`、`target`、`started_at`、`would_finish_at`、`digest_after`；回执 `interrupted=true`。
- 边界：到期点**正好等于**完成时刻不算被截断——那一刻你已经做完了。

**当前接线**（相当确定，我核对了所有 `submit` 调用点）：故事脚本与模型回路调用 `submit` 时都不传 `effects`，所以运行里的动作一口气做完，落在区间里的排程在动作结束后才被 `drain`；中途打断由 `tests/test_m4_deadline.py` 用一张测试替身效果表验证。也就是说，"到点关门把动作切断"这条机制存在且被测试，但现在的故事运行路径还没有把它接上。

### 盘点：一份读数一个出口

`library/stocktake.py` 的 `stocktake(world, eid, include_sealed=False, keep=None)` 返回 `Reading(rows=((名字, 份数), …), total=sum(份数))`。份数只有一个来源——实体的 `count` 状态；默认只数看得见的（封着口的容器里的份数数不到），`include_sealed=True` 数到物理位置里的全部，`keep` 按实体 id 筛选要计入的份数（例如只数现金）。`count` 动词与故事的结局摘要都从这里取数，别处不许再拼一遍同样的加法——否则"数出来的数"会多出一个能与世界脱钩的出口。

### 反作弊三检：各自的实现与抓不住什么

`scripts/anti_cheat.py` 的三项检查都是机械可跑的，但每项都只覆盖它看得见的那一面。

1. **无具名祈使句**：扫描种子里 `prose`、`identity`、`believes[].says`、以及字符串型 `state` 值；出现祈使词（`让`、`应当`、`应该`、`必须`、`务必`、`记得`、`不准`、`不许`、`要他去`、`要她来`）且附近有卡司名，就报失败。**抓不住**：不用这些词下命令的句子；把命令写进排程而不写进文字；实体名/别名里的命令（它不扫这些字段）；以及"有人应当…"这种不点名的命令。`v5_lint.py` 另有一份更宽的祈使词提醒，但它只是提醒，不是失败。
2. **无天意事件**：逐个排程效果检查 `kind` 必须在 `EFFECTS` 里、效果里不许带 `actor`/`say`/`do`、`place` 必须真实存在。**抓不住**：借制度之手替某个具名的人做事的参数（例如 `pickup_due`/`remind` 指定 `who`）——它只证明"不是命运"，不能证明"不是作者借制度之手"；也判断不了这个制度在故事里是否合理。排程效果没有加载期字段白名单，这一检是第二道防线。
3. **结局不唯一**：导入 `stories.<story>.scenario`，对 `SCRIPTS` 里每条写出来的路各跑一遍 `play(variant)`，读 `summary(run)["结局"]` 字符串，要求不同结局的数量不少于路的数量；少于两条路直接失败。**第三检比的是故事自己产出的结局字符串，因此强度部分由故事决定**：它只能看见字符串，不能判断两个标签是否对应真的不同事实，也不能判断结局是否与账本一致；故事的 `summary` 可以返回常量、或返回与事实脱钩的标签。它也只检查写出来的路，没写的路不在范围里；没有 `scenario.py` 时它会跳过（由 lint 的另一条去抓"缺少 scenario.py"）。它跑的是故事代码，是运行时检查，不是静态检查。

## CONFIRMED

- **反作弊第三检不为了指标写假差异**（人确认过）：一条路写两遍就是一条路；脚本能用就继续用，脚本跟实际合理性打架时改脚本；一支故事想要两条路殊途同归，就把它写成一条路。第三检的阈值保持在"不同结局数不少于路数"，它的强度由故事自己的结局字符串承担。

## INFERRED

- **未修的缺陷聚在"故事处境与密度"层**（推的）：表格里大部分条目要在种子、卡司和故事变量上改，引擎侧只剩两处小口子（开门/敲门的物理措辞、模型回合的收尾）。这解释了为什么它们的代价不是"改代码"而是"重写一局并重新生成证据"。
- **检查点续跑与逐字节重放是同一不变式的两个方向**（推的）：一个从中间还原，一个从头重演，两者都要求"事件账 + 原子效果"足以决定世界；任何绕过账本的状态变化都会同时破坏两者。
- **盘点的单一出口消掉一整类错误**（推的）：只要还有第二处自己加份数，读数与结局摘要就可能各自成立却互不相符；一个出口让"数出来的数"只有一种算法。
